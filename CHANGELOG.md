# Changelog

All notable changes to Vidosser. Versions follow [Semantic Versioning](https://semver.org/).

## [1.4.6] - 2026-10-09
### Added
- **Volume drag button** (`volume.drag_button`: `"left"` | `"right"`, default `"left"`; tab: *Volume drag button* / *Botón para arrastrar el volumen* in the Volume section, *Left* / *Izquierdo*, *Right* / *Derecho*). Older `settings.json` files (no `volume.drag_button`) keep the volume drag on the scrub button (`frame_step.drag_button`), i.e. unchanged behaviour; once saved from the tab the value is explicit.
  - **Same button as the scrub** (`frame_step.drag_button`): as before, one press does both and the axis is locked after 4 px by the dominant direction (horizontal = scrub, vertical = volume).
  - **Different buttons**: the volume button's drag is volume only: it starts after 4 px in any direction, only the vertical movement changes the volume, sideways is ignored (no axis lock), and it never scrubs. The scrub button's drag only scrubs: a mostly-vertical drag with it does nothing, but it still counts as a drag (no play/pause toggle or context menu after it).
  - Right button: the context menu is blocked only after a drag (moved ≥ 4 px; Windows opens it on release, so it is skipped then); a plain right click keeps the browser menu. A right-button drag uses pointer capture (no Pointer Lock) and never hides the cursor, in and outside fullscreen (container, gallery and native video fullscreen). The cursor is still hidden only while the LEFT button is held during a drag in fullscreen.
  - Touch is unchanged (a finger does both; a vertical swipe changes the volume only in fullscreen). The volume drag still doesn't interrupt Boomerang going backwards; middle-click save and double-click fullscreen are unchanged.

## [1.4.5] - 2026-10-08
### Added
- **Boomerang loop mode** (`loop.mode`: `"normal"` | `"boomerang"`, default `"normal"`; tab: *Loop mode* / *Modo de bucle* in the Loop section): when a looping video reaches its last frame it plays **backwards** to the first frame, then forwards again, like a bounce — over and over. With an A-B segment it bounces between A and B. It only acts when the video loops (*Loop all videos*, **L**) or has an A-B segment; with the loop off the video simply ends. Older `settings.json` files get `"normal"`.
- **B** key (`keys.toggle_boomerang`, default `"b"`, remappable in *Keys*): Boomerang on/off for the current video, like **L** for the loop (overlay `Boomerang: on/off`, message *Boomerang on (this video)*; if the video doesn't loop, the message says so).
- How backwards playback works: browsers can't play video backwards (no negative `playbackRate` in Chrome), so the video is **paused** while going backwards (silent: no audio at all, volume/mute untouched; sound comes back when it goes forwards) and a clock moves backwards at the current playback speed (0.25–2.00×, read live, so Ctrl + wheel speed works while going backwards). While a Boomerang video plays forwards, Vidosser remembers its frames (downscaled to at most 1280 px, about 256 MB per video, freed when Boomerang is turned off / the video changes; only one video at a time) and shows them backwards on a canvas over the picture at the full frame rate; the video itself follows with exact seeks in the background. Frames not remembered yet (the very first bounce right after loading), the video's native fullscreen and a picture partly off-screen fall back to exact seeks (the next seek only after the previous one finished), which are smooth for small clips and choppier for long-GOP/high-resolution ones.
- Interactions: play/pause (click, space, native button) while going backwards **pauses** it (`Paused (Boomerang, backwards)`), play again continues backwards. A frame step (A / S / wheel / Q / W / Ctrl + wheel jump), a drag scrub or a seek on the progress bar stops going backwards on the frame shown and leaves the video paused; play then goes **forwards**. Save frame (D / middle click) and I / O mark the frame on screen and pause; play continues backwards. The vertical volume drag doesn't interrupt it. Play on a paused last frame goes backwards. Container fullscreen and the new-video no-autojump keep working.

### Added
- **Modifier + wheel action** (`frame_step.wheel_mod_action`, default `"jump"`): choose what holding the configured modifier (Ctrl by default) while turning the wheel does — **Short jump** (unchanged from ≤ 1.4.3: one notch = one short jump, same as W / Q) or **Playback speed** (each notch changes `video.playbackRate` by 0.25, clamped to 0.25–2.00). Overlay `Speed 1.25×` / `Velocidad 1.25×`. The wheel direction that steps frames **forward** also makes playback **faster**; `frame_step.invert_direction` flips both together. Plain wheel and Shift + wheel stay as before. Older `settings.json` files get `"jump"`.
- **Remember playback speed** (`frame_step.speed_remember`, default on): when the action is *Playback speed*, the last rate set with the wheel is applied to videos loaded later (also after a reload; stored in the browser). Only used while the action is speed.

## [1.4.3] - 2026-10-08
### Added
- **Wrap around at the ends** (`frame_step.wrap`, default on): when drag-scrubbing, turning the wheel, stepping with A / S or jumping with Q / W / modifier + wheel, going past the last frame continues at the first one, and going back past the first continues at the last one — as many times as you like in one drag or held key. The overlay shows the wrapped frame number and a ↻ mark when a wrap happened. Off = stop at the first / last frame (≤ 1.4.2 behaviour). The A-B segment loop is unchanged. Older `settings.json` files get the option from the defaults (on).
### Fixed
- With an A-B segment set, a frame step / scrub onto the very last frame of a **paused** video made Chrome fire `ended` (it lands on `duration`), which jumped to the segment start and started playing. A seek-induced `ended` of a paused video is now ignored; playback reaching the end still loops the segment.

## [1.4.2] - 2026-10-08
### Added
- **English / Spanish UI, following the browser language.** Every on-screen text of Vidosser now exists in English and Spanish and is picked from the browser's language (`navigator.languages[0]`, else `navigator.language`): Spanish for any `es-*` (`es`, `es-ES`, `es-MX`, `es-419`…), English for every other language (English is the default and the fallback). Covers the Vidosser tab (labels, help texts, section headers, dropdown / radio choices, buttons, validation and save messages, *Check folder* result) and everything drawn on the video (frame / jump / volume overlays, save / loop / new-video messages, the native-fullscreen subtitle cue, save errors returned by the server). Browser-console logs stay in English.
### Changed
- How it works: Gradio 5.29 (the version WanGP uses) has no `gr.I18n` and WanGP has no UI language setting, so the tab is built in English and, in a Spanish browser, `vidosser.js` writes the language into a hidden textbox of the tab and clicks a hidden button (the same pattern as the save-frame bridge); the server answers with `gr.update()`s carrying the Spanish labels, infos and choices, retried until confirmed. The same hidden textbox is sent with *Save settings* and *Check folder*, and every bridge request carries the page language, so server messages come back in the page's language. Dropdown / radio choices are `(label, value)` pairs: only the labels are translated, the values stored in `settings.json` are unchanged, so existing settings files keep working in both languages.
- The English text is now the default everywhere (it was Spanish only). READMEs updated (English README uses the English labels; new *Language* / *Idioma* section).

## [1.4.1] - 2026-10-08
### Fixed
- **Vertical volume drag in fullscreen.** In 1.4.0 the volume drag used the same Pointer Lock as the scrub and read `movementY` under the lock. Chrome on Windows reports that unreliably: when the lock starts it re-centres the hidden cursor and the first move(s) can carry a jump of up to half the screen (slamming the volume to 0 % or 100 %), and on its raw-input path it can report `buttons = 0` while the button is held, which our missed-release check would take as a release (drag ended at once). Neither happens in headless Chrome, which is why the 1.4.0 tests passed. The volume drag now never takes Pointer Lock: it reads `clientY` under pointer capture (exact, real button state; the screen gives far more travel than 0–100 %), in every fullscreen mode (Vidosser's container fullscreen, Gradio's gallery fullscreen button, native `<video>` fullscreen) and outside fullscreen.
- Scrub under Pointer Lock hardened against the same quirks: movements larger than 60 px in the first moves around the lock start are ignored (cursor re-centring), `buttons = 0` is not treated as a missed release while locked (pointerup ends the drag; a `mouseup` backup was added).
- **Overlay in native `<video>` fullscreen**: nothing can be drawn above a natively fullscreen video, so the overlay (volume, frame, save, loop) is shown there as a cue of a "Vidosser" subtitles track at the top left (Chrome's captions button is hidden on that video if it had no captions of its own; the cue is cleared on leaving fullscreen). A video never played since loading is nudged out of its poster state (seek to the same time) so the cue is displayed.
### Changed
- **Cursor policy**: the cursor is hidden ONLY while the LEFT mouse button is held during a drag (scrub or volume) in fullscreen, and restored immediately on button up / cancel / Esc / blur. Outside fullscreen drags work with a visible cursor and pointer capture (no Pointer Lock); right-button drags never hide the cursor or lock it. Pointer Lock is only used for a horizontal left-button scrub in fullscreen (`drag_pointer_lock`); `drag_hide_cursor` applies only to left-button drags in fullscreen.
- Chrome's own idle cursor hiding (its native controls set `cursor: none` when they fade out over a playing video, inline and in fullscreen) is overridden, so the cursor never disappears while idle.
- Tab texts for *Bloquear el puntero al arrastrar*, *Ocultar el cursor mientras arrastras* and the *Volumen* section updated.

## [1.4.0] - 2026-10-08
### Added
- **Volume by vertical drag** (`volume.drag_volume`, default on): click and hold on a video and drag vertically, up = louder, down = quieter, `volume.drag_pixels_per_percent` px per 1 % (default 2, 0.2–50), `volume.drag_invert` (default off). Shares the gesture with drag-to-scrub: the axis is decided once, when the pointer has moved 4 px, by the dominant direction (|dy| > |dx| = vertical, a tie = horizontal, as before) and stays locked until release, so a scrub never changes the volume and a volume drag never scrubs. Overlay `Volumen ██████░░░░  60 %`; clamped to 0–100 % and re-anchored at the limits; whole percents; raising a muted video unmutes it from 0 %. A volume drag doesn't pause the video, uses the same button (`frame_step.drag_button`), pointer lock and hidden cursor as the scrub, and swallows the click that ends it; plain click and double-click (fullscreen toggle) are unchanged. Works in and outside fullscreen (container and native). Touch: a vertical swipe changes the volume only in fullscreen (`touch-action: pinch-zoom` there); outside fullscreen it still scrolls the page. With `drag_scrub` off the vertical volume drag still works (and vice versa). `volume.remember` (default on): the last volume (drag or native slider) is applied to videos loaded later, also after a reload (localStorage); muting is never remembered.
- **New video while fullscreen** (`new_video.no_autojump_fullscreen`, default on): while a gallery video is fullscreen (Vidosser's container fullscreen, Gradio's gallery fullscreen or native `<video>` fullscreen), a newly generated video no longer replaces it: position, play/pause, volume, loop and fullscreen are kept and the video isn't even reloaded. Gradio's gallery keeps the preview `<video>` and only sets its `src`; that one change is refused while fullscreen, then the watched video's thumbnail is re-selected, so Gradio and WanGP (`select_media`) select it again and later refreshes keep it. The same update sent twice counts once. The new video is added to the gallery as usual, with the message *Nuevo vídeo listo (sigues viendo este)* / *N vídeos nuevos listos* (`new_video.notify`). Outside fullscreen WanGP jumps as before; the user's own navigation (thumbnail click, arrow keys) is never blocked; if the watched video leaves the gallery the change is applied. `new_video.jump_on_fullscreen_exit` (default on): leaving fullscreen shows the newest video, i.e. what WanGP would have done, so the gallery keeps following new videos outside fullscreen.
- New tab sections **Volumen** and **Vídeo nuevo**. Settings files of older versions get the new sections from the defaults.

## [1.3.0] - 2026-10-07
### Added
- "Repetir todos los vídeos en bucle" (loop all videos) is now on by default.
- **Drag to scrub**: hold the left mouse button (or a finger) on a video and drag horizontally to step frames, `frame_step.drag_pixels_per_frame` px per frame (default 8), right = forward (`drag_invert`). Position based, exact integer targets through the same seek queue (no drift). Starts after a 4 px mostly-horizontal threshold, so a plain click still toggles play/pause; pauses the video on drag start and swallows the click that ends a drag. Uses **Pointer Lock** while dragging (`frame_step.drag_pointer_lock`, default on): the pointer is hidden and can't hit the screen edge; Chrome/Edge show their "Press Esc to show your cursor" banner each time. The lock is always released on button release, Esc, window blur, tab hidden or cancel. If the lock is off or refused, it falls back to pointer capture (keeps working outside the video) with the cursor hidden during the drag (`frame_step.drag_hide_cursor`, default on; class on `<html>`, the video and the fullscreen element), always restored on release, cancel, lost capture, Esc, blur or a missed release. Esc during a drag only ends the drag (it no longer closes the gallery preview). Shift + drag = `shift_frames` per step, short-jump modifier + drag = one short jump per step. Not used on the native control bar (bottom 40 px of `<video controls>`, only while the controls are shown), thumbnails or other elements. Works in and outside fullscreen (container and native), independent of `wheel_fullscreen_only`. Setting `frame_step.drag_scrub` (default on). `frame_step.drag_button`: `left` (default) or `right`; with the right button the context menu is blocked only after an actual drag, so a plain right click keeps the normal menu (on macOS/Linux the menu opens on press, so use the left button there). All options in the tab.
- **Short jump with the wheel**: holding a modifier while turning the wheel makes each notch one short jump (the same size as `W`/`Q`). Setting `frame_step.wheel_jump_modifier`: `ctrl` (default), `alt`, `shift`, `meta` or `none` (dropdown in the tab). With `shift`, the jump takes precedence over `shift_frames` and the tab shows a note. The browser zoom (Ctrl + wheel) is blocked only while Vidosser is actually stepping a video. Trackpad pinch gestures (synthetic Ctrl + wheel) are accumulated into whole jumps. Respects `wheel_fullscreen_only` and `invert_direction`, and the overlay shows the jump.
- **Save feedback**: prominent message *Fotograma guardado (frame N): name/path* (2.5 s, fades out; drawn inside the fullscreen element when a container is fullscreen), red error message, grey message on cancel, white flash over the video, and a WebAudio camera-shutter sound (error: low double beep). Settings `save_frame.toast`, `toast_ms`, `flash`, `sound`, `sound_volume`.
- **Fullscreen with overlays** (`general.container_fullscreen`, default on): double-clicking a video or using the fullscreen button of WanGP's video player puts the player box fullscreen instead of the bare `<video>`, so the overlay, messages and loop bar are visible. The fullscreen button in the browser's native control bar can't be intercepted and stays native. **Double-click toggles**: inside fullscreen (container or native) it exits, outside it enters; the double-click's two clicks don't change the play state; a double-click right after a drag is ignored, and drag / pointer lock / click swallowing never eat a following double-click.
- **Hide the control bar** (`general.hide_controls`: `off`, `fullscreen` (default) or `always`, dropdown in the tab): hides the browser's `<video>` controls (removing the `controls` attribute, plus CSS for Chrome's forced controls in native fullscreen) and WanGP's player bar in fullscreen; restored on fullscreen exit or when switched off. Click and Space still play/pause, and the whole picture is draggable (no 40 px exclusion). `general.show_thin_progress` (default on): a 3 px non-interactive progress line at the bottom edge of the picture while the controls are hidden (not in native fullscreen).
- **Loop module**: `loop.loop_all` (loop every video, live, including videos added later); `L` toggles looping of the current video; frame-accurate **A-B segment loop** with `I` (in), `O` (out) and `U` (clear). Out before in is swapped; moving one end past the other end of a complete segment starts a new segment. Segments are per video and kept while the page is open, shown as a thin 3 px line on the picture's top edge (so nothing covers the bottom), and confirmed by messages. Stepping is never clamped to the segment.
- New keys are listed in the tab's key list, with duplicate-key validation across all actions. If an existing `settings.json` already uses one of the new default keys, the user's key wins and the new action gets a free key.
### Changed
- The jump settings are grouped as **Salto corto** in the tab (used by `W`/`Q` and modifier + wheel).
### Fixed
- Status messages in the tab carry the time, so two saves in a row are visibly confirmed.
- Stepping backwards from the very end of a video (`currentTime == duration`, e.g. after it ended) could skip one frame.

## [1.2.0] - 2026-10-07
### Added
- **Middle click (wheel click) saves the frame** over a video, or anywhere while a video or its container is fullscreen. Same as `D`, using the configured format, mode and folder. It saves exactly once per click, suppresses Windows/Chrome autoscroll, Linux paste and `auxclick`, and ignores a slight wheel roll while pressed. Middle clicks elsewhere (links, buttons, gallery thumbnails) are untouched. Setting `save_frame.middle_click_save` (default on).
- **`frame_step.wheel_fullscreen_only`** (default on): the wheel steps frames only while a video (or an element containing one) is fullscreen. Outside fullscreen the wheel is not intercepted at all. Keys and middle click are not affected.
### Changed
- `settings.json` is no longer shipped. It is created by the Vidosser tab, ignored by git, and preserved across updates. Missing keys (e.g. from a 1.1.0 file) are filled from the built-in defaults; the 1.0 key layout is migrated automatically.

## [1.1.0] - 2026-10-07
### Added
- Renamed to **Vidosser**, a collection of video viewing tools (folder/id `wan2gp-vidosser`), structured as a core plus modules.
- Keyboard frame stepping: `A`/`S` previous/next frame, `Q`/`W` jump back/forward (0.5 s converted with the video's fps, or N frames).
- **Save frame** (`D`): exact displayed frame at full resolution, extracted server-side from the source video with WanGP's decoder. PNG or JPG (quality), *ask* (Save-as dialog) or *direct* (auto-numbered, never-overwriting files in a folder) mode.
- **Vidosser settings tab**: key capture, frame-stepping options, save options with folder check, overlay; validated, saved to `settings.json`, applied live.
### Fixed
- Chrome could stay stuck "seeking" when several seeks were issued quickly. Seeks are now queued, with a watchdog.

## [1.0.0] - 2026-10-07
### Added
- Mouse-wheel frame stepping in the WanGP UI, also in fullscreen: one wheel notch = exactly one frame (no acceleration or coalescing loss), Shift + wheel = 10 frames, exact fps detection from MP4/MOV/MKV/WebM headers, overlay with frame number.
